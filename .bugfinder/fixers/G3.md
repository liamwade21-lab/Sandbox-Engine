# Fixer G3: planet tilt for the surface generator, frame-time clock drift

## Files you own (edit only these)
crates/se_core/src/surface_gen.rs, climate.rs (and climate/tests.rs), rotation.rs,
crates/se_engine/src/universe.rs

## Items
- 02-5 (low; findings/02.md, verdicts/02.md, read the verdict carefully): the surface generator
  uses obliquity 0 for catalog bodies the completion ran on that have no top-level `Obliquity`
  (and ignores a `Rotation { Obliquity }` sub-block). SE sets the generator's tropicLatitude from
  sat(sin(FUN_140515e50(...))) (FUN_1402f37c0 around lines 465-476), where FUN_140515e50 measures
  the angle between the body's spin axis and the orbit normal of its top-level planet (the tilt
  relative to that orbit). For tidally locked bodies that is 0 (so the port is right for Proxima b
  and TRAPPIST-1 e; don't break them). Port that measure: compute the same angle from the body's
  rotation model and its (top-level) orbit, and feed it to the generator in place of the raw value.
  Verify with the RE tools against FUN_140515e50 before coding. Check Earth, Mars and a few
  exoplanets with unlocked rotation give sensible tropicLatitude values, and that bodies with an
  explicit Obliquity relative to the ecliptic still match SE.
- 03-5 (low; findings/03.md, verdicts/03.md): in frame-time mode (`RealTime false`) the clock adds
  dt*rate/86400 to a Julian date of ~2.46e6 every frame, which rounds the same way each frame:
  -2.2 s per hour at 60 fps. Keep an anchor (the date when the clock was last set or the rate
  changed) plus elapsed simulated seconds, and compute the date from those, re-anchoring wherever
  the date is set or the rate changes. Find every place that writes the date (grep for writes to
  the sim clock's `jd`) — if any are outside universe.rs, make the anchor robust to them (e.g.
  re-anchor when `jd` differs from what universe.rs last wrote) instead of editing those files.
  Real-time mode must behave exactly as now.
