# Ticket 08 findings (start-up and memory), hunter report verbatim

Summary: 8 findings, best first. The two biggest are confirmed in real port runs with a test build:
- The ~830 ms worst frame: Bevy's background thread pool is capped at 4 threads and the galaxy builds fill it. Raising the cap to 8 cut the worst frame to 206-225 ms.
- ~350 MB of peak memory: galaxy sprite meshes are kept in main memory as well as on the GPU. Dropping that copy cut the peak from 2019-2060 MB to 1685 MB.

All measured changes on together: startup segment mean 17.6-18.4 ms / max 830-860 ms / 1% low 2 fps / peak 2019-2060 MB → mean 13.7 ms / max 192 ms / 1% low 7 fps / peak 1686 MB.

08-1 | crates/se_engine/src/main.rs:87-90 | Bevy's default AsyncComputeTaskPool has 4 threads (25%, max 4), shared by every port loader: 39 galaxy and 4 nebula model builds, 169 procgalaxy nodes, atmosphere preload, procstars, procsystems, terrain. Bevy also builds its render pipelines on that pool. On the first frame, prepare_view_upscaling_pipelines calls block_on_render_pipeline, and its task waits behind the galaxy builds: one 676.6 ms call in the trace, which is the 800+ ms frame. 15 galaxy models finish in the same frame right after the stall. | Give async_compute a fixed 8 threads (min 8, max 8) in TaskPoolOptions; the compute pool still gets the rest of the 24 hardware threads. Tidier long term: a separate small pool for model builds, so pipeline tasks never queue behind them. | Measured: worst start-up frame 833/857 → 225/206 ms (2 runs each), mean 17.6/18.4 → 15.6 ms, 1% low 2 → 5 fps. 12 threads was worse (max 336 ms, peak 2423 MB). 8 threads alone raises peak memory 80-140 MB (more builds hold buffers at once); 08-2 more than pays that back. | low: only task timing changes. The final picture is identical, but the frame on which a model or procedural galaxy first appears can shift. Procedural galaxy catalog ids (RG → 11066+) are given out in node-finish order, which already depends on timing. | .optimize/scratch/08/tr/frames.txt (trace of frame 2); runs base_a/base_b vs async8_a/async8_b/async12 in .optimize/scratch/08/runs; experiment.diff

08-2 | crates/se_engine/src/galaxies.rs:457-468, 602-633 | Galaxy and nebula sprite meshes use RenderAssetUsages::default(), so the full 4-vertex-per-sprite mesh stays in main memory on top of the GPU copy. It is kept only so SpriteOrder can swap the index buffer. At start-up that is 1.376M sprites × 232 B = ~320 MB (Mars scene: 2.57M sprites, ~600 MB). Each re-sort and each first upload also clones the whole ~11 MB mesh during extract (extract_render_asset<RenderMesh> up to 38 ms). | Make the meshes RENDER_WORLD and keep a compact per-sprite copy (pos, data, info = 44 B/sprite; the centres are already kept) in an Arc on SpriteOrder. The sort task rebuilds the expanded vertex arrays plus sorted indices off the main thread; the main thread just puts the new Mesh into the same handle. | Measured with RENDER_WORLD and sorting off: peak 2019-2060 → 1685 MB (-350 MB) in start. Estimated -280 MB steady state after keeping the 44 B/sprite copy, -500 MB in mars. Also removes the up-to-38 ms extract clone per re-sort. | none: same vertex data, same sorted indices, same draw order | experiment runs galrw and all8; sprite counts summed from base1/*.png.log

08-3 | crates/se_engine/src/atmosphere.rs:129 (also :138) | While the atmosphere preload is still running, get_or_load tests whether a file exists with vfs.read(path).is_err(). Each .atm is 17 MB and takes ~75 ms to inflate. The model is still not cached afterwards, so load_atmosphere reads and inflates it again (75 ms), parses it (16 ms) and converts it to f16, all on the main thread, while the preload task reads the same file a third time. This is why spawn_system_members takes 108-118 ms a frame despite its 4 ms budget. | Use vfs.is_readable(path) for the test. Better: while the preload runs, return Pending for any model it will deliver (the body already waits via PendingAtmosphere), which avoids the duplicate synchronous load. | Measured (is_readable only): "entered system Solar System" 743 → 236 ms. Removes ~75 ms per first use of each of the 13 .atm models during start-up; estimated ~90 ms more with the Pending change. | none for is_readable (differs only for a corrupt .atm); low for Pending (the atmosphere appears a few frames later at start-up, then looks the same) | bench: "13 .atm files, 221.7 MB, one read 75.6 ms, exists() 0.006 ms"; run atm_memo

08-4 | crates/se_engine/src/stars.rs:418-429 (se_core/src/star.rs:353) | build_catalog_starfield calls blackbody_rgb for each of 129,723 stars (81 wavelengths × 9 exp calls each): 305-326 ms of the 652 ms first (Startup) frame. setup_galaxies and setup_nebulae wait behind it on the same thread. The catalog has only 5416 distinct Teff values. | Memoise in a HashMap keyed by teff.to_bits() inside the loop. Neutron stars and black holes keep their special colours. Splitting the loop across ComputeTaskPool chunks would also work. | Measured: 305-326 → 25 ms per launch (in-port log line). Bench: 406 → 26 ms, same sum. | none: the exact same f64 input gives the exact same f32 output | bench08 "memoised blackbody 25.8 ms, 5416 distinct teff, same sum true"; run atm_memo log "catalog starfield ... in 25ms"

08-5 | crates/se_engine/src/data.rs:61-137 | All of DataPlugin::build (902 ms in the trace) runs serially on the main thread, after ~550 ms of other plugin builds (RenderPlugin 340 ms for the wgpu device; PBR, audio, core pipeline ~200 ms), so the window opens ~1.5 s after launch. Inside it, the ephemeris load (~240 ms, almost all inflating the 102 MB DE436 file) runs after the catalog instead of alongside it. | Start mount + catalog + ephemeris on a std::thread at the top of main() and join it in DataPlugin::build; load the ephemeris on its own thread next to Catalog::load. Buffer the log lines and print them after the join (the logger isn't installed yet). | Estimated 600-900 ms less to first window: the data work (~860 ms, ~620 ms with the ephemeris in parallel) mostly hides behind the 550 ms of other plugin builds | none: same data, same order | trace top2000.txt plugin build times; bench08 "ephemeris read 241 ms", "Catalog::load 504-529 ms"

08-6 | crates/se_core/src/catalog.rs:391-426, 644-704, 471-484 | Catalog::load reads and parses its 67 files serially (read+inflate 46 ms, sc::parse 109 ms). The HIPPARCOS.csv merge alone takes 190-198 ms: ~65 ms of per-row work (field parse, SpectralClass, powf), the rest name registration. Each name is lowercased twice (existing() and register()), and the names map grows from empty with SipHash. | Read and parse files in parallel, then merge in the original order (load_doc). Split CSV row parsing into parallel chunks, keeping existing/register/push in row order. Compute key() once per name, reserve the names/exact maps up front, and optionally use a faster hasher (nothing can rely on map order, since the std hasher is already randomised per run). | Measured: parallel read+parse 155 → 35 ms; the serial merge of those parsed docs gives the same catalog. Estimated Catalog::load ~520 → ~330 ms. Off the critical path if 08-5 is done. | none: merge order unchanged (fingerprint of stars/bodies/galaxies/clusters/nebulae equal) | bench08 "parallel read+parse (12 threads) 35 ms", "parallel == serial (pre-resolve): true", "HIPPARCOS load_star_csv 194 ms; row work alone 65 ms"

08-7 | crates/se_engine/src/atmosphere.rs:164-178 (table_image/f16_bytes :353) | The preload task returns all 13 atmosphere tables as f32 (~221 MB), and they stay in memory until upload_preloaded pops them, one per frame. Each pop converts ~4M floats to f16 on the main thread (upload_preloaded up to 22 ms/frame for ~7-13 frames). This adds to the transient start-up peak (working set 1450 → 1955 MB about 5 s after launch). | Do the f16 conversion inside the preload task and hand over ready Rgba16Float byte buffers (or built Images). That halves the memory held (~110 MB) and moves the conversion off the main thread. | Estimated ~-110 MB transient peak and -15-20 ms on ~10 start-up frames | none: same f16_bytes() result | trace: upload_preloaded 146.8 ms total, max 22.06 ms; bench: 13 × 17 MB tables; memory timeline .optimize/scratch/08/m1/start.mem.txt

08-8 | Bevy render thread: allocate_and_free_meshes / prepare_assets<GpuImage> (from galaxies.rs/nebulae.rs model meshes + front textures) | After the stall, frames 3-8 still take 70-213 ms on the render thread (allocate_and_free_meshes 38-164 ms, prepare_assets<GpuImage> 11-92 ms): the 39 resident model meshes (~11 MB each), the procgalaxy mesh and 505 galaxy / 222 nebula textures all arrive in the same few frames. | Spread the uploads: hand finished models to Assets at most N MB per frame, in a fixed queue order. 08-2's smaller extracted meshes also help. | Estimated start-up p99 89-146 → ~40 ms. 08-1..08-4 combined measured mean 13.7 ms, max 192 ms, 1% low 7 fps, peak 1686 MB (baseline 17.6-18.4 / 833-857 / 2 fps / 2019-2060 MB). | low: a model appears a frame or two later during loading; once loaded the picture is identical | trace frames at 3.067-3.585 s in .optimize/scratch/08/tr/frames.txt; run all8
