# Verdicts for tickets 06 (GPU) and 08 (start-up), verifier report verbatim

06-1 | needs-call | measured (hunter, SE_SOLID_RES=0.5 proxy) | ~3 ms GPU in the Skylias interior at 1600x900, more at bigger windows; the frame is CPU-bound there (~6 ms), so it shortens only at large windows | medium | Confirmed volume_resolution is read (graphics.rs:126) and shown on the settings slider but used nowhere. Rendering at VolumResolution and upscaling deliberately changes the picture (toward SE), so it's the user's call. The implementer must composite premultiplied, since the nebula outputs premultiplied (tone*img.x, (1-grey)*img.y).

06-2 | needs-call | measured | 0.6-0.85 ms GPU in Skylias, 0.15 ms in the RN scene | medium | The branch is on a uniform (vol.f) and the spiral noise has no texture sampling, so control flow is safe. But the scalar loop compiles differently from the vec2 one (fma contraction, how division becomes a reciprocal), and the hunter's A/B found 2% of pixels more than 1% off. A visual change.

06-3 | needs-call | measured | 0.4-0.5 ms GPU | low | Specializing on flags lets the compiler fold maths differently, so pixels shift slightly (99.94% within 1e-3). Each new flag combination also compiles a pipeline in the background, so that nebula is missing for a few frames the first time it appears: a design decision.

06-4 | recommend | measured | ~0.1 ms GPU (within run-to-run noise) | none | Checked galaxy_nebula_raymarch.wesl:406-428: gas_color and invalid are only read inside `if ndb < gas_h`, sum_t is unchanged between the loop and the branch, and the loop has no texture/derivative calls. Moving it inside only skips dead work. Small gain, trivial change.

06-5 | recommend (with condition) | measured | 0.45-0.6 ms GPU on Earth's opaque pass; no frame-time change while that scene is CPU-bound | low | The hunter's "explicit gradients, so the branch is safe" is wrong: sample_layer (planet.wesl:708-709) calls dpdx(p)/dpdy(p) itself, and putting biome_look(k2) under the per-pixel `t > 0` places those derivatives in non-uniform control flow. naga doesn't reject it (DISABLE_UNIFORMITY_REQ_FOR_FRAGMENT_STAGE = true), but results are undefined in quads where only some pixels have t > 0, and could break on other drivers even though the hunter's screenshot matched. Condition: compute p, dx, dy for k2's large and small layers outside the branch and pass them in; only the texture sampling and relief go inside. With that the output is identical: biome_albedo has one caller (planet.wesl:2319, inside the uniform biomes.flags.x branch); w1/w2 can't become NaN (only updated through > comparisons); t stays in [0, 0.5] (denominator ≥ 1e-4); b2 is always finite (all divisions guarded), so mix(b1, b2, 0) == b1 exactly; the k2 == 5 rock_tint multiply and the grad/rough/k mixes all reduce to b1.

06-6 | drop | measured | under 0.1 ms (not measurable) | low | min(distance, 0) is always 0, but the hunter's A/B shows every pixel shifting up to 1e-3 from compiler regrouping. No measurable gain, and pixels change.

08-1 | recommend (with condition) | measured | worst start-up frame ~830 → 210 ms, 1% low 2 → 5 fps | low | Only task timing changes. Procedural galaxy promotion (procgalaxies.rs promote_near) already depends on node readiness, so RG ids and the frame a model appears were already timing-dependent. Conditions: don't override the user's MaxThreads (the patch sets 8 even when with_num_threads(n) applies; use something like min(8, total/3)); scale down on low-core machines; ship together with 08-2, because alone it adds 80-140 MB of peak memory.

08-2 | recommend (with condition) | measured (peak, sorting off) + estimated (steady) | ~280-350 MB peak at start-up, ~500 MB in the Mars scene, plus no more 11 MB extract clone (up to 38 ms) per re-sort | low | On the main thread, the only readers of the galaxy/nebula sprite meshes from into_mesh are SpriteOrder's get_mut/insert_indices (galaxies.rs:619). Nothing reads attributes back, there's no mesh picking, and capture, screenshots and the projection cube faces all draw from the render world. The entities have NoFrustumCulling, so no Aabb is computed from the main-world mesh. Conditions: the rebuilt mesh must be byte-identical to into_mesh (all attributes and corners, plus the 2 pad_aabb vertices), with sorted indices from the same back_to_front, inserted into the same handle. Don't apply it to the far nebula mesh (nebulae.rs:492), which is edited in place via attribute_mut at nebulae.rs:627.

08-3 | recommend (is_readable part only) | measured | "entered system" 743 → 236 ms; 75 ms of main-thread inflate saved per model on first use | none | is_readable matches read().is_err() except for a corrupt/unreadable .atm, which now reaches Missing at once instead of after the preload, with the same end result. Reject the "return Pending" extension: the preload task also generates cfg-only models (~12 s each, atmosphere.rs:110-115) and hands back its whole list only at the end, so on a first run every atmosphere would wait for all the generation to finish.

08-4 | recommend | measured | ~280-300 ms off the first (Startup) frame (305-326 → 25 ms in the port's log) | none | blackbody_rgb (star.rs:353) depends only on teff (no other star field or setting goes in). Black holes take the disk_light branch before this point and neutron stars keep their fixed colour, so star_render_color is a pure function of (kind, teff) for the memoised cases. Keying on teff.to_bits() is exact (±0 or other NaN bit patterns just make extra entries with the same result). Keep the BlackHole and NeutronStar exclusions.

08-5 | recommend (with condition) | estimated | ~550-800 ms less before the window opens | none | DataPlugin::build depends only on EngineConfig (built from command-line args and env vars before the plugins, never written later), and se_core's catalog/vfs code doesn't log. Conditions: join in DataPlugin::build at the same point and insert the resources there; emit the info/warn lines (mounted, ephemeris, catalogs, the CatalogLog-filtered warnings) at the join in their original order, with timings measured on the thread; exit(1) on a mount failure at the join; join the ephemeris before catalog.de is set and before complete_catalog_orbits; don't use Bevy task pools on that thread (they don't exist yet).

08-6 | recommend (with condition) | measured (parallel read+parse) + estimated (whole load) | Catalog::load ~520 → 330 ms; only ~70 ms of that shows once 08-5 is in | none | CSV row parsing (catalog.rs:661-697) is pure; existing/register/push depend on earlier rows, so they must stay serial in row order. names and exact are HashMaps that are never iterated, so changing the hasher or reserving space can't change anything. Conditions: merge in list_ext order (stars csv, then sc, then planets, galaxies csv before sc, clusters, nebulae); push read-error and header warnings in their original order; compute key(names[0]) once, as existing does; use std::thread::scope, not Bevy pools.

08-7 | recommend (with condition) | estimated | ~110 MB less transient peak and ~15-20 ms off ~10 start-up frames | none | The parsed f32 tables are only read by upload_tables (atmosphere.rs:133-135, 173-176); only params is kept afterwards. Conditions: convert to f16 after the cache-file write (to_bytes needs the f32 tables); keep params, the pop order and the cap/clear logic.

08-8 | needs-call | estimated (not measured) | start-up p99 maybe 89-146 → ~40 ms | low | Spreading uploads delays when models appear during loading, and the per-frame budget N is a design choice. Partly overlaps 08-2 (which already cuts extract/upload size); re-measure after 08-2 before building it.
